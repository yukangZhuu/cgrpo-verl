# Dataset Migration: 100+28 anchors → pure 128 unsolvable

## Background

The original adaptive curriculum training used
[data/ttn2k/final/ttn_unsolvable_pass64_max2600_n100/dataset_adaptive.jsonl](../data/ttn2k/final/ttn_unsolvable_pass64_max2600_n100/dataset_adaptive.jsonl):

- 100 unsolvable problems (pass@64 = 0)
- 14 of those problems duplicated as frozen anchors at `g_level = 0.0`
- 14 of those problems duplicated as frozen anchors at `g_level = 1.0`
- Total 128 rows, matching `data.train_batch_size = 128`.

The 28 anchors were added purely to fill the batch. They had no other
methodological role.

## Why the anchors are a problem under MFC

Under GRPO, a rollout group produces zero advantage whenever reward variance
is zero within the group. For anchors:

- `frozen_g_level = 0` anchors are unsolvable with no guidance. Every
  rollout fails; `reward_variance ≈ 0`; **zero gradient**.
- `frozen_g_level = 1` anchors reveal all but the last teacher step. Every
  rollout succeeds; `reward_variance ≈ 0`; **zero gradient**.

Worse, under MFC's distribution-shift framing, `g_level = 1` anchors train
the policy on a heavily shifted input distribution that we do **not** test
on — they leak shift-only gradient.

Under MFC's headline surrogate, `frac_at_zero`, the `g=0` anchors would
permanently inflate the metric by `14/128 ≈ 11%`. That contaminates the
central figure of the paper.

AdaBack is also impacted (even though it was not designed with MFC in mind),
because the 14 `g=0` anchors in `dataset_adaptive.jsonl` are exactly the
samples that AdaBack's original run counted toward `frac_at_zero ≈ 0.45` —
so the "true" AdaBack self-resolve rate is closer to `(0.45 − 14/128) = 0.34`.

## New dataset: pure 128 unsolvable

[data/ttn2k/final/ttn_unsolvable_pass64_n128/dataset.jsonl](../data/ttn2k/final/ttn_unsolvable_pass64_n128/dataset.jsonl)

- **Source**: [data/ttn2k/final/ttn_unsolvable_pass64.jsonl](../data/ttn2k/final/ttn_unsolvable_pass64.jsonl) (136 rows, all `pass_rate = 0`).
- **Selection**: stable sort by `(question_chars + steps_chars, index)` ascending, keep the first 128.
- **Rationale for "shortest 128"**: deterministic (no RNG), maximises compatibility with `data.max_prompt_length = 2500`, preserves all problems with low-to-moderate step counts.
- **Schema per row**: source fields (`index`, `question`, `pass_count`, `pass_rate`, `ground_truth`, `steps`) + `adaptive_id = str(index)`. No `frozen_g_level`, no `g_level`, no `guidance_steps`.
- **Length stats** (after selection): min=668, median=2037, max=2941 chars.
- **Dropped rows** (8 longest; kept as reference in the report file): indices 13761, 13675, 18333, 8289, 14866, 18722, 8043, 15081 (roughly — see [report.json](../data/ttn2k/final/ttn_unsolvable_pass64_n128/report.json) for the authoritative list).
- **Build script**: [scripts/teacher_traces/build_ttn_unsolvable_n128.py](../scripts/teacher_traces/build_ttn_unsolvable_n128.py).

The old anchor dataset remains on disk and is not deleted; it is referenced
by `run_ttn2k_unsolvable_adaptive_hint_8xpro6000.sh` (original launcher,
kept as historical).

## Required code change

`CurriculumGRPODataset.__getitem__` previously only emitted the `g_level = -1`
sentinel (which tells the trainer to compute `rho` dynamically) for
`curriculum_method == "adaptive"`. With MFC, this check is widened to
`curriculum_method in ("adaptive", "mfc")`. Without this fix, MFC rows
would silently train with `g_level = 0.0` and the MFC state would never
advance.

See the diff in [verl/utils/dataset/curriculum_dataset.py](../verl/utils/dataset/curriculum_dataset.py).

identical between the n128 AdaBack and n128 MFC launchers.

## Reproducibility

To rebuild the pure-128 dataset from scratch:

```bash
python3 scripts/teacher_traces/build_ttn_unsolvable_n128.py
```

This is deterministic; it should produce a byte-identical file on any
machine given the same source jsonl.
